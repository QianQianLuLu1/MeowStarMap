# NikkiGallery 项目全量审查与轻量化优化方案

> 审查对象：`wxnn-photo-manager`（无限暖暖相册管理工具）v2.3.5，Electron 40 + React 19 + TypeScript 5.9
> 审查类型：全量代码审查 + 功能设计审查 + 轻量化删改方案（只删不改健壮性）
> 审查日期：2026-08-14
> 审查方法：结构通读（架构文档 / package.json / 构建配置 / 入口与生命周期）+ 分区深挖（主进程 14 个 app 模块、30 个 IPC handler、12 个 service、17 个 utils、数据层 4 进程、渲染层 stores/hooks/pages/components）+ 逐项证据复核（Grep/Read 二次验证，剔除误报）

## 1. 审查概述

### 1.1 总体结论

- **功能完整度与健壮性处于较高水准。** 项目在生命周期（单实例锁 3 重试 + 三选项弹窗、before-quit 异步清理 + WAL 动态超时强制退出兜底）、安全（`wrapHandler` + zod + `PathGuard` 路径白名单 + `media://` 协议 5 层白名单）、并发（3 个 utilityProcess + 自研分级调度）等方向均有成体系的设计，并附有大量 `P0/P1/C-x` 修复注释，可追溯性好。
- **未发现致命级缺陷。** 本审查未复核到会导致数据丢失、崩溃或权限越界的致命/严重级代码缺陷（详见 §2.2.5 对疑似项的证据排除）。
- **主要冗余集中在"未被生产代码引用的死代码"与"同一工具函数的两套实现"。** 合计可删/可并约 1000+ 行源码，删改不影响任何运行路径。
- **文档与实现存在多处漂移**（且文档内部自相矛盾），会误导后续维护与发布决策，需一并修订。

## 2. 分维度问题 + 优化/删改方案

### 2.1 功能设计审查

#### 2.1.1 业务流与需求匹配（结论：良好）

| 能力域        | 审查结论                                                                                                                                                       |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 媒体扫描      | 首启强制全盘 + 增量 + 签名，游戏目录 5 级查找优先级（用户自定义 → 硬编码 → Steam 注册表 → Epic 注册表 → 全盘签名搜索），含符号链接/深度/系统目录防护，设计完整 |
| 图库浏览      | 5 视图 + 虚拟滚动 + 多档缩略图 + LRU，覆盖充分                                                                                                                 |
| 编辑/视频     | 22 项调整 + 历史栈 + 批量；视频裁剪/调速/转换/Live Photo，功能闭环                                                                                             |
| 重复/相似检测 | SHA256 + pHash 双通道 + BK-tree 半径检索（O(n²) → O(n log n)）+ 4 维评分，实现优于文档宣称                                                                     |
| 回收站        | 三阶段事务 + 中断可重试，幂等设计正确                                                                                                                          |
| 分享/备份     | 剪贴板 4 层渠道检测 + WiFi PIN 鉴权 + Range；备份 7 天最小间隔 + 5 份 LRU                                                                                      |
| 安全          | contextIsolation + sandbox + PathGuard 默认拒绝 + 5 层 media:// 白名单 + zod 校验，成体系                                                                      |

#### 2.1.2 功能冗余 / 投入产出待评估（一般，产品决策）

- **F1｜插件系统为"重资产、轻使用"。** `pluggable-electron` + `plugin-host.ts` + `permission-guard.ts` + `plugin-runtime.ts` + `plugin.ts`（IPC）+ 插件文档体系，而 `plugins-samples/` 仅 1 个示例。若插件长期无真实用户接入，该链路是持续维护负担。
  - 方案：先评估插件安装/使用数据，若低，将插件系统标记为"冻结维护"（不删，避免破坏文档承诺的 API），并明确不为其新增能力。
- **F2｜分享码解码（ShareCodeDecoderDialog）与"媒体加密" Tab。** 与核心相册整理主流程关联度低，疑似为外围功能。建议确认是否仍被真实使用；未使用可下线入口、保留代码。
- **F3｜自动更新未启用代码签名。** `package.json#build.win.signAndEditExecutable=false` 且 `verifyUpdateCodeSignature=false`。electron-updater 链路已接入（`app/auto-update.ts`），但未签名安装包更新会被 Windows SmartScreen / 杀软拦截，功能处于"半成品"状态。
  - 方案：属于发布决策，不删代码；若短期无法获得代码签名证书，建议在设置页明确提示"自动更新可能被系统拦截"或改为手动下载入口，避免用户误判。

#### 2.1.3 边界与异常处理（结论：优秀）

单实例锁失败三选项、WAL 按大小动态超时、`media://` Range 越界回 416（`media-protocol.ts:79-88`）、损坏文件容错（`injectCorruptedMarkers`）、缺失检测/孤儿清理、`startup-errors.log` 独立落盘等均有明确兜底，无缺口。

### 2.2 全量代码审查

#### 2.2.1 无效代码 / 死代码（可安全删除，收益最高）

**D1｜`src/main/utils/safe-execute.ts` 为生产死代码（约 370 行 + 测试文件）。**（一般）

- 证据：全 `src` 范围内，`safeExecute / safeExecuteSync / safeExecuteOrThrow / resultToIpcResponse / errorToIpcResponse / wrapAsync / wrapAsyncThrow / databaseErrorMapper / fileSystemErrorMapper` 的唯一引用来自其自身测试 `safe-execute.test.ts`；所有 handler/service 均未引用（错误映射职责已由 `validator.ts` 的 `wrapHandler` 承担，两者职责本就重叠）。
- 建议：整模块 + 测试文件删除。若担心将来需要"恢复执行 + 记录错误"语义，可保留 `safeExecuteOrThrow` 一个函数（约 60 行），其余删除。

**D2｜`src/common/utils/*` 为生产死代码，且与渲染层工具重复（约 200 行 + 测试）。**（一般）

- 证据：`src/common/utils/`（`index/string/date/format/id/object/path`）的唯一引用来自 `common-utils.test.ts`；`src/main` 与 `src/renderer` 均无 `@common/utils` 或相对路径引用。其注释宣称"主进程与渲染进程共享"，实际无人使用。
- 建议（二选一）：
  1. **推荐**：统一到一处——渲染层删除 `renderer/utils/format.ts`、`renderer/utils/date.ts`，改用 `common/utils` 的 `formatSize/formatDate` 等（vite alias `@common` 已配置），随后保留唯一实现；或
  2. 反向：以 `renderer/utils` 为准，删除整个 `common/utils`（含测试）。本项目主进程无消费者，方案 2 更轻，但会留下"工具散落渲染层"的结构。
  - 影响面：改约 10 个渲染层文件的 import 路径（`../../utils/format` → `@common/utils`）。删除前运行 `npm run typecheck && npm test` 验证无引用遗漏。

#### 2.2.2 重复逻辑（可合并）

**R1｜`format/date` 存在两套实现。**（一般，与 D2 同源）

- `renderer/utils/format.ts`（`formatSize/formatFileSize/formatEta`）与 `common/utils/format.ts`（`formatSize/formatFileSize`）重复；`renderer/utils/date.ts`（`formatDate`）与 `common/utils/date.ts`（`formatDate/formatDateTime/formatTimestamp/formatCompactTimestamp/formatDateOrDash/formatDuration`）重复。
- 建议：随 D2 一并收敛为一套，消除"改一个、漏一个"的分叉风险。

**R2｜`src/main/utils/scene-category.ts` 是纯 re-export 桥接。**（一般，低优先）

- `scene-category.ts:8` 仅 `export * from '../../shared/scene-category'`。引用方：`connection.ts:7`、`scanner/worker-entry.ts:28`、`scanner/worker-protocol.ts:11`（type）、`utils/scene-brightness.ts:6`（type）、`ipc/handlers/media-handler.ts:9`（type）。
- 建议：将上述 5 处 import 改指 `shared/scene-category`，删除桥接文件。注意 `scene-category.test.ts` 与 `shared` 下无冲突即可。

**R3｜`repair-legacy-data-v1/v3/v4` 模式高度同构。**（一般，可选）

- 三个独立模块均为"查询 → 修复 → 标记迁移状态 → 失败记录"三段式（v3 约 70 行、v4 约 70 行），且 v2 仍内联在 `worker-entry.ts`（约 20 行），模块化程度不一致。
- 建议：仅当后续再新增 v5 时，重构为"版本号 + 修复函数表"的单一入口；当前各自有独立测试（`repair-legacy-data-v1.test.ts`），不建议立即合并（投入产出比低）。

#### 2.2.4 规范 / 性能隐患

**P1｜大型文件（可读性/测试聚焦风险，非 Bug）。**（一般）

- `scanner/worker-entry.ts` 1524 行、`database/media-repository.ts` 1450 行、`pages/DuplicatesPage.tsx` 1339 行、`pages/GalleryPage.tsx` 726 行。
- 建议：不强制拆分（改动风险 > 收益）；但新增改动时按"扫描器状态机 / SQL 组装 / 重复清理策略"等内聚主题小步抽离，避免继续膨胀。

**P2｜i18n 硬编码与 TODO 堆积。**（一般）

- `shared/errors/app-error.ts:201/218/235` 的 `userMessage` 为中文硬编码（`// TODO: i18n`）；主进程大量 `TODO: i18n: internal log`（`lifecycle.ts` 等）；`renderer/utils/game-events.ts` 版本/活动名存储中文文案（`TODO: i18n`）。
- 建议：错误 `userMessage` 仅影响提示语，不影响功能；建议新增面向用户的错误统一走 i18n，主进程日志可不强制翻译（内部日志）。列入技术债清单即可，勿一次性大面积改动。

**P3｜脚本/配置冗余。**（一般）

- `package.json:38-39` `dev` 与 `dev:ev` 完全重复（均 `electron-vite dev`），删 `dev:ev`。
- `tsconfig.phase3-check.json` 无任何 npm script 引用（仅 `docs/PROJECT-OVERVIEW.md` 提及"phase3 隔离检查"），疑似迁移遗留；确认后删除。
- `ts-node` 仅在 `scripts/perf-test/*` 的注释/文档中手动使用（npm scripts 均已改用 `tsx`），与 `tsx` 并存不一致；可将 perf-test 手动命令统一为 `tsx` 后移除 `ts-node`（devDependency）。
- 结论：以上三个 `*.ps1`（`pre-build-cleanup.ps1 / post-reboot-cleanup.ps1 / fix-build-lock.ps1`）经核实**未被 package.json 任何 script 引用**，若历史构建流水线已不使用，可归档到 `scripts/archive/`（建议先归档不删除，属排查性结论）。
