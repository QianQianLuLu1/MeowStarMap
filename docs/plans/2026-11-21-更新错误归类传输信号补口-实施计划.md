# 实施计划：更新错误归类传输信号补口（修复「网络可达 GitHub 仍弹『未获取到可用的更新信息』」）

- 日期：2026-11-21
- 轮次目标：设置 › 应用信息与联系方式 › 检查更新，在网络可访问 GitHub 的前提下仍弹出「未获取到可用的更新信息，点击确定跳转官网」错误弹窗的根因修复。
- 改动约束：仅改归类器判据（1 个源文件 + 2 个测试文件 + 2 个文档）；零新增依赖；严格红灯→绿灯。

## 一、根因分析（Context）

弹窗文案 = i18n `settings.about.updateSourceUnavailable`（`src/renderer/i18n/locales/zh-CN.json:1746`），由 `src/renderer/components/common/UpdateDialog.tsx:253-257` 在主进程推送的 `payload.errorKind === 'source'` 时渲染。errorKind 由主进程 `src/main/app/update-error-class.ts` 的 `classifyUpdateError()` 决定（`src/main/app/auto-update.ts:152` error 事件 / `:187` catch 兜底）。

契约（`src/shared/types/electron-api.ts:420-426`）明确：

- `network` = 连不上更新源（DNS / 拒连 / **超时** / TLS / 5xx / 429）
- `source` = 连得上但更新源未就绪（缺 latest.yml / 无已发布版本 / feed 解析失败 / 其余 4xx）

核对 electron-updater 6.8.9（node_modules）真实抛错形状后，确认 3 处「传输层失败被误归为 source」的缺口。GitHub 可达但链路不稳 / 被限流时恰好命中这些形状，弹出错误弹窗：

| #   | 真实错误形状                                                                                                                                                                                                                     | 出处                                                                                                     | 现归类                                                                                 | 契约要求                                                             |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 1   | `Error("Request timed out")`（无 code、无 statusCode）                                                                                                                                                                           | `node_modules/builder-util-runtime/out/httpExecutor.js:282`（60s socket 超时，`request.abort()` 后抛出） | source ❌（"REQUEST TIMED OUT" 不含 `ETIMEDOUT`，不匹配 NETWORK_SIGNAL/NETWORK_CODES） | network                                                              |
| 2   | `Error("Request has been aborted by the server")`（无 code）                                                                                                                                                                     | `httpExecutor.js:145`（响应中途被服务端断开）                                                            | source ❌                                                                              | network                                                              |
| 3   | `ERR_UPDATER_LATEST_VERSION_NOT_FOUND` 包装错误：`getLatestTagName()` 把 `/releases/latest` 的**任何**失败（含 403 限流、5xx）包成普通 Error，`statusCode` 属性丢失，仅剩 message 内嵌文本 `HttpError: 403 rate limit exceeded…` | `node_modules/electron-updater/out/providers/GitHubProvider.js:158-175`                                  | source ❌（statusOf 提取不到状态码，落入 `ERR_UPDATER_` 前缀分支）                     | network（403/5xx⇒network，`update-error-class.ts:120-121` 注释意图） |

by-design 不改项：`…/download/<tag>/latest.yml` 404 ⇒ `ERR_UPDATER_CHANNEL_FILE_NOT_FOUND` ⇒ source 属正确行为（2026-11-05 轮取证并测试锁定）。CI（`.github/workflows/build.yml` softprops/action-gh-release）已随 tag 上传 `release/latest*.yml`。GitHub 完全可达且通道文件就绪时，正常链路只会得到「已是最新版本」或更新提示——弹错误框即说明某次请求失败且被误归 source，与上表 3 处缺口吻合。

## 四、错误处理（异常分支、兜底、日志）

- `classifyUpdateError` 保持「永不抛错」契约：入参 unknown（Error / 字符串 / null / Proxy / throwing getter）全部经既有 `safeGet` / `asRecord` / `causeChain` 收窄，本轮新增判据只做字符串正则匹配，不新增任何可抛点。
- 兜底方向不变：仍 `source`（`update-error-class.test.ts:174-176` 锁定）；新判据只把「能确证是传输层失败」的形状转回 network，不做反向扩大。
- 日志规则不变：归类结果照旧以 `errorKind=<kind>` 进主进程日志（`auto-update.ts:153`），渲染端弹窗不显示技术串。

## 五、参数校验

- 输入域：`classifyUpdateError(err: unknown)` 不校验类型、不抛错，未知形状一律兜底 source；本轮新增正则仅作用于 `textOf` 收窄后的 string。
- 新状态码提取要求 `HttpError:` 后紧跟 3 位数字（`/HttpError:\s*(\d{3})/i`）；`HttpError: Response code 404` 等既有形态不受影响（"Response" 非数字，不误提取）。
- 边界：cause 链深度仍 `MAX_CAUSE_DEPTH=8` 封顶；seen 集合挡循环引用（既有测试钉住）。

## 六、基础测试用例

- 正常场景：latest.yml 404 ⇒ source、无发布版本 ⇒ source（既有用例保持绿）。
- 异常场景：本轮新增 4 条 network 用例（超时 / 服务端断开 / 包装 403 / 包装 502）+ 集成 1 条（error 事件推 `errorKind:'network'`）。
- 边界场景：包装内嵌 404 ⇒ 仍 source（防过度矫正）；包装内嵌 ENOTFOUND ⇒ 仍 network（顺序契约）；throwing getter / Proxy / 循环 cause 不抛（既有）；兜底 source（既有）。
