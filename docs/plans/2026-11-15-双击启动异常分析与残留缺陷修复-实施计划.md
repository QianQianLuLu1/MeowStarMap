- 日期：2026-11-15
- 版本基线：meow-star-map v2.5.7-beta（Electron 41 + React 19 + TypeScript 5.9）
- 上游计划：`docs/plans/2026-11-15-双击启动三类异常收尾与残余根因修复-实施计划.md`（R1/R2 轮，其 N2 的 lifecycle 死代码清理未完成，由本计划节点 A 收尾）
- **已确认决策**：① 问题电脑现象来自旧版本（优先部署复测）；② 本轮执行残留缺陷 A（lifecycle 死代码）+ B（second-instance ack 静默让位）修复；③ 与上游计划口径一致：不执行 git 提交，由用户统一提交。

## 0. 结论摘要

1. 三类现象（无响应 / 闪退无提示 / "已有实例运行"）在旧版本上各有明确根因，绝大多数已被 F1-F6 / R1 / P0 / P1 系列修复覆盖，正确动作是**打包部署 + 按验收清单复测**。
2. 当前代码仍存在两处确定残留缺陷，本轮按 TDD 闭环修复：
   - **缺陷 A**：`src/main/app/lifecycle.ts` L74-240 残留一套与 `src/main/app/single-instance.ts` 重复的内联单实例锁死代码（R1 迁移漏删）。生产不可达（index.ts 已在重模块加载前获取锁），但 `lifecycle.test.ts` 仍在测该死分支，绿灯失真。
   - **缺陷 B**：健康首实例正在运行（含托盘/启动中）时再次双击，第二实例静默重试 6 秒后**仍弹出"已有实例运行"警告框**——窗口已聚焦却又弹报错，用户感知为异常；极端慢启动下用户点"清理并重启"还会误杀正在启动的健康实例。
3. 修复方案：B 采用 **second-instance ack 标记**机制（首实例响应第二实例请求时写存活标记；第二实例重试耗尽后检测到新鲜标记即静默让位，不弹框）。零新增依赖。

## 1. 当前启动链路（代码实读结论）

```
快捷方式 → MeowStarMap.exe
└─ index.ts 模块加载期
   ├─ uncaughtException / unhandledRejection 先注册（reportEarlyFatal：弹框+落盘+退出）

   ├─ GPU 三级兼容阶梯决策（ready 前；level≥1 禁硬件加速，≥2 加 --disable-gpu）
   └─ app.whenReady()
      ├─ ① acquireSingleInstanceLockOrHandleFailure()        ← R1 前移（重模块加载前）
      │     赢家→继续；失败→6×1s 重试→三选项对话框（清理并重启/手动处理/退出）
      ├─ ② verifyStartupEnvironment()（userData 不可写→阻塞式双语弹窗）
      ├─ ③ registerRendererProtocol()
      ├─ ④ 动态 import Application + 构造 16 服务              ← 杀软扫描热点窗口
      └─ ⑤ application.initialize() → bootstrapApplication
          ├─ （残留死代码：二次 requestSingleInstanceLock —— 节点 A 删除）
          ├─ 注册 second-instance 处理器（restore/show/focus；0 窗口按启动状态兜底）
          ├─ initExitForensics / verifyCriticalNativeModules / markBootAttempt / GPU watcher
          ├─ 阶段1 DB init（最重）→ 2 目录迁移 → 3 logger+i18n → 4 crashReporter
          ├─ 阶段5 备份 → 6 协议+IPC+createMainWindow（首窗）→ initNikkiSyncRuntime（F6 后移）
          ├─ 阶段7 主题+修复 → 8 延迟任务（低优先级队列，首窗 ready-to-show 后 resume）
          └─ 退出链：before-quit → performCleanup（动态超时 2-5s）→ 释放锁 → app.exit(0)
```

## 2. 三类现象归因与关联

### 现象 1：双击无响应（无窗口、无提示）

| 根因                                                                          | 旧版本是否存在 | 当前代码状态                                      |
| ----------------------------------------------------------------------------- | -------------- | ------------------------------------------------- |
| NikkiSync 运行时全盘发现阻塞首窗（未装游戏机器实测 ~14s）                     | 是（直接机制） | ✅ F6 已移到首窗之后                              |
| 锁获取在 16 服务构造之后，慢机+杀软下第二双击抢先拿锁、首实例反被判"已有实例" | 是             | ✅ R1 前移修复                                    |
| initialize 失败进程不退出、无窗口无日志变僵尸                                 | 是             | ✅ fatal catch + 弹窗 + 释放锁 + exit(1)          |
| GPU FATAL "GPU process isn't usable. Goodbye."（int 3 同步自杀，JS 无异常）   | 是             | ✅ 三级阶梯结构性预防                             |
| 锁失败实例 6×1s 重试期完全无可见反馈                                          | 是             | ⚠️ 残留（缺陷 B 部分缓解：健康赢家会聚焦窗口）    |
| DB init 等 8 阶段先于首窗，慢机首窗延迟数秒                                   | 是             | ⚠️ 设计取舍（有 diag.log 面包屑可取证；不本轮改） |
| 杀软直接拦截进程启动（无进程产生）                                            | 可能           | ❌ 代码无法防护 → 取证裁决                        |

### 现象 2：短暂启动后闪退无提示

| 根因                                             | 旧版本是否存在 | 当前代码状态                           |
| ------------------------------------------------ | -------------- | -------------------------------------- |
| GPU/驱动兼容 FATAL（历史 54 个 dump 裁决的主因） | 是             | ✅ 三级阶梯 + 自愈 relaunch            |
| VC++ 运行库缺失 / ABI 不匹配静默崩溃             | 是             | ✅ native-load-guard 同步双语弹窗      |
| initialize 失败后僵尸化（伴生现象 3）            | 是             | ✅ 已修                                |
| ffmpeg 子进程持事件循环导致退出挂起持锁          | 是             | ✅ cleanup kill + 强制 exit 兜底       |
| crashReporter 阶段 4 才启动（更早崩溃无 dmp）    | 是             | ⚠️ chromium-debug.log 补位（不本轮改） |
| 杀软强杀（无 JS 痕迹）                           | 可能           | ⚠️ 心跳取证补位 → 取证裁决             |

### 现象 3：反复双击后"已有实例运行"提示

该提示（`zh-CN.json` `main.dialog.instanceRunning.*`："应用已在运行中…"）**本身是设计内的单实例保护**，非异常报错。触发条件：6×1s 重试全部失败（锁被他人持有）。以下场景使它"看起来像 bug"：

| 场景                                                                                     | 旧版本 | 当前代码状态                             |
| ---------------------------------------------------------------------------------------- | ------ | ---------------------------------------- |
| 首实例健康运行（含托盘/隐藏）：第二双击→窗口已聚焦，6s 后**又**弹警告框                  | 是     | ❌ **残留缺陷 B（本轮修）**              |
| 首实例启动中（慢机+杀软，窗口未出）：loser 6s 后弹框，用户点"清理并重启"误杀健康启动实例 | 是     | ❌ **残留缺陷 B 覆盖（ack 机制一并修）** |
| 关闭后立即重开：before-quit WAL checkpoint 2-5s 持锁                                     | 是     | ✅ F4 6×1s 重试覆盖                      |
| 僵尸进程持锁（旧版 initialize 失败残留）                                                 | 是     | ✅ 源头已修 + 三选项清理                 |
| taskkill 杀不死 crashpad_handler 子进程                                                  | 是     | ✅ /F /T /PID 递归杀                     |
| wmic 在 Win11 24H2 已移除                                                                | 是     | ✅ PowerShell -EncodedCommand            |
| 实例角色颠倒（见现象 1）                                                                 | 是     | ✅ R1 修复                               |
| 多版本共存（per-user + per-machine 双安装）                                              | 可能   | ❌ 代码无法防护 → 取证裁决               |

**关联关系**：三类现象同源于"启动链路在异构 Windows 环境（杀软 / GPU 驱动 / 运行库 / 慢盘）下的可见性与互斥协议"。现象 1/2 是首实例链路问题；现象 3 是互斥协议问题；旧版本中现象 2 的僵尸进程直接制造现象 3。共同环境放大器：杀毒软件实时扫描。

## 3. 根因列表（按可能性排序，针对问题电脑的旧版本现象）

1. **慢机 + 杀软实时扫描**：启动慢 → 用户重复双击 → 旧版锁获取太晚导致实例角色颠倒 / 误弹框（R1+F4 已修，部署即消）
2. **GPU/驱动兼容 FATAL**：历史主因（54 dump 裁决；三级阶梯已修）
3. **NikkiSync 全盘发现阻塞首窗 ~14s**（F6 已修）
4. **旧版 initialize 失败僵尸持锁**（已修）
5. **VC++ 运行库缺失**（已修，有弹窗引导）
6. **残留缺陷 B**：健康实例运行时误弹"已有实例运行"（本轮修）
7. **环境特定因素**（代码无法防护，取证裁决）：杀软直接拦截/隔离、Documents 重定向（OneDrive）致取证缺失、多版本共存、快捷方式指向失效路径
8. **死代码 A**：非直接致障，但双真相源 + 测试绿灯失真是回归温床（本轮清理）

### 依赖声明

- **零新增依赖**。仅 Electron `app` / Node `fs` / 现有 `diagLog`。
- 修改文件（6 个）：
  - `src/main/app/single-instance.ts`（缺陷 B：ack 读/写 + 静默让位）
  - `src/main/index.ts`（缺陷 B：锁获取成功后最早注册 ack 写入监听）
  - `src/main/app/lifecycle.ts`（缺陷 A：删除 L74-240 死代码块）
  - `src/main/app/__tests__/single-instance.test.ts`（B 用例）
  - `src/main/app/__tests__/lifecycle.test.ts`（A 用例清理 + 守护用例）

  - `e2e/second-instance.e2e.ts`（B 修复后第二实例预期从"停在对话框"改为"静默退出"，同步调整断言）

### 节点 A：删除 lifecycle.ts 残留锁死代码

- **文件**：`src/main/app/lifecycle.ts`
- **改动**：删除 L74-240 的 `requestSingleInstanceLock` 二次获取 + 重试 + `!gotLock` 对话框整块（含 `lockAcquired` 变量）；fatal catch 中 `if (lockAcquired)` 分支简化为无条件 `releaseSingleInstanceLock` + `app.exit(1)`（bootstrap 仅由赢家调用，index.ts 已保证）。保留 `second-instance` 处理器注册与全部 8 阶段逻辑。同步清理仅被死代码使用的 import（`execFileSync` / `exec` / `clearDeathEvidenceForRelaunch`）。
- **测试（红灯→绿灯）**：
  1. 红灯：lifecycle.test.ts 用例 1 改写为守护用例——"bootstrapApplication 全程不调用 requestSingleInstanceLock、不弹 instanceRunning 对话框"（当前代码调用 → 失败）。
  2. 删除死代码 → 该用例转绿。
  3. 删除 lifecycle.test.ts 中已等价覆盖于 single-instance.test.ts 的锁失败路径用例（1c/2/3/4/5/6/6b/7/E1/36）；保留 second-instance 处理器（8/S1-S6）、8 阶段、before-quit、fatal catch 用例；用例 12/35 注释随 lockAcquired 移除同步订正。
- **验收标准**：守护用例通过；`npx vitest run src/main/app/__tests__/lifecycle.test.ts src/main/app/__tests__/single-instance.test.ts` 全绿。

### 节点 B：second-instance ack 静默让位（现象 3 核心修复）

**机制设计**：

- ack 文件：`userData/second-instance-ack.json`，内容 `{"pid": <赢家pid>, "ts": <epoch ms>}`（pid 仅供诊断，不参与判定）。
- **写入方（赢家）**：`index.ts` 在 `acquireSingleInstanceLockOrHandleFailure()` 返回 true 后**立即**注册 `app.on('second-instance', () => writeSecondInstanceAck())`——位于动态 import Application 之前，覆盖"杀软扫描热点窗口"内发生的第二次双击（lifecycle 的完整 handler 稍后注册，两个监听器并存无冲突：前者写 ack，后者聚焦窗口）。
- **读取方（输家）**：single-instance.ts 中 6 次重试全部失败后、`await app.whenReady()` 弹框**之前**检查 ack：新鲜（`now - ts ≤ 15000ms`）→ 判定赢家存活且刚响应 → `diagLog` 留痕 + `app.quit()` + `return false`，**不弹框**；否则走既有三选项对话框。
- **为什么只在重试耗尽后检查（不能提前退出）**：ack 无法区分"健康运行"与"正在退出途中"——before-quit 清理期（2-5s）的赢家也会写 ack，若输家提前退出会破坏 F4"关闭后立即重开"场景。重试期内锁若释放，输家自然拿到锁成为新赢家，走不到 ack 检查。
- **僵尸判定保持**：僵尸/挂死进程的事件循环不运行 → 不写 ack（或 ack 陈旧）→ 弹框 → "清理并重启"路径不变。

**参数校验（ack 解析容错，全部 fail-open）**：文件不存在 / 读抛错 / JSON 损坏 / 缺 `ts` / `ts` 非数字或 NaN / `ts > now + 1s`（未来时间，时钟异常保护）→ 一律视为"无新鲜 ack"→ 走弹框。写入失败静默（fail-open，不影响窗口聚焦）。

**错误处理**：写 ack 在监听器内 try/catch 吞错；静默让位路径 `diagLog('BOOT', ...)` 留痕供诊断包裁决；输家侧不新增弹窗路径（沿用既有 `showStartupFailureWithFallback` 兜底链）。

**测试用例（先行红灯）**：

| 类别 | 用例                                                                                              | 预期                       |
| ---- | ------------------------------------------------------------------------------------------------- | -------------------------- |
| 正常 | 锁 6 次重试失败 + ack 新鲜（真实临时目录 + 真实 fs）                                              | `app.quit()`，**零对话框** |
| 正常 | ack 新鲜且 pid 与当前进程不同                                                                     | 同上（pid 不参与判定）     |
| 异常 | ack 文件不存在 / readFileSync 抛错                                                                | 弹三选项框                 |
| 异常 | ack JSON 损坏 / ts 为字符串                                                                       | 弹三选项框                 |
| 边界 | 检查时刻 age = 14999ms（fake timers 钉死时钟）                                                    | 静默退出                   |
| 边界 | 检查时刻 age = 15001ms                                                                            | 弹三选项框                 |
| 边界 | `ts = 检查时刻 + 5000`（未来）                                                                    | 弹三选项框                 |
| 单元 | `writeSecondInstanceAck()` 正常写入 `{pid, ts}`；写入失败（userData 指向文件下的非法路径）不抛出  | fail-open                  |
| 静态 | startup-entry-guard.test.ts：index.ts 中 ack 监听注册位于锁获取之后、动态 import 之前             | 守卫防回退                 |
| e2e  | second-instance.e2e.ts X2/X3：健康主实例下第二实例 ~6s 后自行退出、证据文件零污染、主实例不受影响 | X1-X3 调整后全绿           |
