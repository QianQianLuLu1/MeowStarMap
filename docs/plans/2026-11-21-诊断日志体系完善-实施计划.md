# MeowStarMap 诊断日志体系系统性完善 — 实施计划

## 1. Context（为什么做）

上一轮「排查 Electron 闪屏根因」（会话 9719b1b8）暴露三大教训：取证信息不足（关键时刻无日志）、日志分散（多落点/多格式/应急文件不进包）、根因难定位（exitDiagnosis 绕过 ring buffer、设置变更无痕、IPC 失败静默）。本次对「导出诊断包」日志体系做系统性完善，三目标：**扩大覆盖（已授权不脱敏）→ 单一体系完全互通 → 不引入稳定性问题**。

用户已拍板决策：

- **A** 取消语义维持主进程 `throw AppError.canceled`，渲染端三入口统一 CANCELED 静默，删死 `canceled` 分支。
- **B** 批准移除 `sanitizeAggregate` 脱敏（反转钉住测试，不弱化其他断言）。
- **C** FeedbackDialog 描述接通：`log:exportZip` 新增可选参数，描述+勾选写入包内 `feedback.txt`；**勾选不裁剪包内容**（诊断包恒含全部日志，勾选仅记录用户意愿）。
- **D** `exportLogsAsZip` 返回补 `filePath`，成功 Toast 统一展示真实路径。
- **E** 移除设置页 `faultCount===0` 禁用导出的条件。

## 3. 统一方案设计

### 3.1 bootId 与行格式（单一体系的时间线骨架）

- 新增 `src/main/utils/boot-id.ts`：**零依赖叶子模块**，模块加载期 `crypto.randomUUID()`，导出 `BOOT_ID` / `BOOT_ID_SHORT`(8 位)。原因：exit-forensics 的 bootId 在 whenReady 才生成，logger 可被更早懒初始化，不能复用（已核实时序）。
- `logger.ts:221` 行格式 → `[ISO] [LEVEL] [b:<boot8> p:<pid>] msg`。已核实既有 52 个 logger 测试全为 `toContain('[INFO]')` 子串断言，不破坏。tag 约定为 message 前缀 `[Boot]/[Settings]/[Window]/[GPU]/[IPC]/[PathGuard]/[NikkiSync]/[Update]/[Plugin]/[DB]/[Worker]`（与 scan bridge 既有 `[Stage]` 前缀解析兼容）。
- `FaultRecord` 增可选 `bootId`；`buildFaultRecord` 导出供 cleanup 复用；recentLogs 附带名单增 `ipcError`。
- `exit-forensics.ts:363-366` 改用 `BOOT_ID`（heartbeat/last-exit 与主日志同 bootId，可拼接）。
- **不新增第二套写入器**：全部新日志点复用 logger.info/warn/error/fault；electron-log 双写保留（同模块内冗余兜底，main.log 已在 2GB 目录清理范围）。

### 3.2 cleanup exitDiagnosis 修复（保住退出竞态约束）

`cleanup.ts:197-211` 改用导出的 `buildFaultRecord` 构造（含 recentLogs+环境+bootId），**仍用 `fs.appendFileSync` 同步写**——原注释明示异步 appendFile 会拖延 app.exit（P0 修复），不得换 logFaultSync（其副作用含异步写）。

### 3.3 IPC 可观测性：单点拦截器（替代 48 文件机械迁移）

全项目 250 处 `ipcMain.handle` 分布在 47 个 handler 文件，但**全部经 `app/ipc-setup.ts` 的 `setupIPC()` 注册**。新增 `src/main/ipc/ipc-observability.ts`（纯函数，注入 ipcMain 形状便于单测）：在 setupIPC 注册期临时包装 `ipcMain.handle(channel, listener)`，注册完成后还原（若核实存在 setupIPC 之外的懒注册则改为常驻幂等包装）。拦截器逻辑（全程 fail-open try/catch）：

- `performance.now()` 计时；响应 `success===false` 时：CANCELED 静默；VALIDATION_ERROR → `logger.warn('[IPC]', {channel, issues})`；其余 → `logFault('ipcError', …, {channel, code, details})`（激活闲置 FaultType）。
- 耗时 **>500ms** → `logger.warn('[IPC] slow', {channel, ms})`（正常 handler <50ms，500ms 覆盖慢盘/锁等待且误报低；热路径仅两次计时调用，成功且快则零写盘）。
- listener 抛错（wrap* 之外的异常）→ 记 fault 后原样 rethrow，不改变契约。
- PathGuard 拒绝的**完整路径**在守卫抛出点补记：`validator.ts` assertFileRead/WritePath 与 `media-read-guard.ts` 拒绝分支 `logger.warn('[PathGuard] deny', {path 完整, reason})`（IPC 错误 details 的 maskPath 保持不变——那是对外契约，日志侧记全量）。

### 3.4 diag.log 轮转与应急落点收编

- diag.log：内存字节计数（首写 statSync 一次），**>1MB rename 为 `diag.log.old`（覆盖旧 .old）后重开**——保完整历史、尾部永不丢（优于 startup-errors 的 100KB 重置）。`FORENSICS_ROOT_FILE_NAMES` 增 `diag.log.old`；导出两者均尾部 2MB。
- `startup-diagnostic.ts` 导出 `getDiagLogPathValue()`（真实写路径，应急态导出侧不再漏收）；`logger.ts` 导出纯函数 `getEmergencyLogCandidates()`（APPDATA/meow-star-map/logs/main.log、tmpdir/meow-star-map-logs/main.log、tmpdir/MeowStarMap-{diag,startup-errors}.log）。导出时探测存在者收入 `fallback/`，manifest 登记来源。**不改应急写入逻辑本身**（fail-open 兜底语义不变）。
- chromium 日志截断增强：copyBounded 截断 chromium-debug.log 时，同步流式扫全文件提取 `/FATAL|exit_code/` 行写入 `chromium-debug.highlights.txt`（上限 500 行），保证头部关键取证不因尾部策略丢失。

## 4. 五要素（用户执行约束要求）

1. **依赖声明**：**零新增依赖**。boot-id 用 node:crypto；zip 沿用 archiver；electron-log 沿用。不重装 node_modules（保护 @nikkisync 链接与 package-lock）。
2. **启动说明**：环境即现有开发环境；验证命令全部为 package.json 真实脚本：`npm run dev`、`npm test`、`npm run test:main`、`npm run test:renderer`、`npm run typecheck`、`npm run lint`、`npm run i18n:guard`、`npm run verify`、定向 `npx vitest run <路径>`。
3. **错误处理**：所有新日志点 fail-open（try/catch 静默或降级 diagLog）；拦截器不改变 IPC 响应契约；导出恒 settle（沿用 zip-archive 单出口）；cleanup 保持纯同步写；应急兜底写入逻辑不变。
4. **参数校验**：`log:exportZip` options 为可选对象，zod 校验 description≤2000 字符串、两布尔可选；非法参数 → VALIDATION_ERROR（被拦截器记 warn）；无参调用完全向后兼容。settings 值截断 1KB；chromium highlights 上限 500 行；diag.log 1MB 轮转。
5. **基础测试用例**：每节点正常/异常/边界三类齐备（见各阶段红灯测试表），如：导出正常含 feedback.txt / 描述超 2000 拒 / 无参兼容；diag.log 未超限不轮转 / 超限 .old 完整 / 应急路径可读；拦截器成功快调用零日志 / 失败记 fault / CANCELED 静默 / 慢调用 warn。
