## 1. 目标与范围

1. **兼容层**：把「链接升级到 b422193」后仍停留在 d4ca7d7 形状的本仓静态面收敛到位——vendored 协议/域类型真相源、探针必需导出表、深入口产物核查清单、装载面结构声明、打包产物断言；迁移 SQL 确认零适配并落档老库安全分析。
2. **能力层**：对上游 1.0.5→1.0.23 期间新增的 PC 侧能力逐项接入，每个能力一个独立节点，各自携带「主进程服务 → IPC handler/preload 桥契约 → Zustand/页面组件 → i18n（12 语种，zh-CN 基准）→ 设置键白名单/错误码」完整分层改动与独立提交。
3. **明确的裁决**：13 项上游新能力中 5 项判「不做」（§11），其余 8 项进入节点；破坏性能力（批量删除）的确认/可逆语义在节点内定义并列入待确认（§14）。

**边界事实（决定节点形状的三条，全部已亲自核实）**：

- 本仓编排**不调** `PcCompanionRuntime.start()`（它会无条件 `server.start()` 绑 `0.0.0.0`），只调 `scanner.start()`；因此上游六阶段回调（`PcStartupStage`）在本仓编排下不会自然发生，启动阶段观测必须由本仓 `runtime-manager` 在自身编排点自报**真实发生**的阶段，不得照抄上游枚举谎报未执行的阶段（如 `dictionary-enrichment`）。
- `PcCompanionRuntime` 构造期**必然**组装 `DeletionQueue` 并注入 `LocalSyncServer`（`runtime.ts:65,93`）：链接升级后 `POST /v1/organizer/sync` 已经激活；但其执行依赖 `NIKKISYNC_RECYCLE_HELPER` env（上游用 windows-shell 自身充当 helper，本仓必须自备，见 K8-a）。
- `scanDiagnosticSummary` / `ExtraScanDirectories` / `CachedDecodedMetadataService` / `MetadataOnlineConsent` / `LanAddress` / `GameVersionCalendar` 均为**深入口**（不在各包桶导出内，`scanner/index.ts` 的 `export *` 清单已核实不含 ScanDiagnostics），一律走 `runtime-facade` 既有深入口装载模式，不进 `NIKKISYNC_REQUIRED_EXPORTS`。

## 6. 能力层节点详单

通用分层规则（每个能力节点逐条对照，缺一不可）：

- **主进程**：逻辑落 `src/main/nikkisync/`（状态机/编排）与 `src/main/nikkisync/sync-server-view.ts` 或新纯函数文件（可单测面）；装配缝在 `src/main/app/nikkisync-runtime-setup.ts`。
- **IPC**：通道注册在 `src/main/ipc/handlers/nikkisync-handler.ts`（受保护路径，实质改动须携 `// @core-change: <真实中文原因>`，本节点原因例如「新增 nikkisync:organizer-* 整理队列通道」）；zod schema 沿既有 `wrapHandler`/`wrapHandlerNoArgs`/`wrapHandlerRaw` 家族；错误归一沿 `toAppError`，**不新增 AppError 错误码**（复用 `VALIDATION_ERROR/NOT_FOUND/PRECONDITION_FAILED/INTERNAL_ERROR`）。
- **preload**：`src/main/preload/api/nikkisync.ts` 增方法（受保护路径，携同批 `@core-change`）+ `src/main/preload.ts` 无需动（命名空间已组装）+ `src/renderer/vite-env.d.ts` 类型镜像。
- **契约文档**：`docs/IPC_CONTRACT.md` §8 增「阶段 2 能力扩展」小节，逐通道给出入参/出参/失败码。
- **i18n**：key 落 `syncService.*` 既有子树；流程 = zh-CN 先行 → `npm run sync-i18n-keys`（其余 11 locale 补空串）→ 补齐 11 语翻译 → `npm run i18n:check` 绿 + `npm run i18n:guard` 绿 + 扩展 locale key 守卫测试 `src/renderer/i18n/locales/sync-service-keys.test.ts`。
- **上游中文串不透传**：上游 `state().message` / `lastResult` 为上游硬编码中文，本仓 UI 一律按**英文短码/状态枚举**映射本仓 i18n key，不原样渲染上游中文。

## 7. 错误处理与参数校验总纲

1. **外部输入不可信**：所有新 IPC 通道入参过 zod（沿 `nikkisync-handler.ts` 既有 schema 风格；长度上限 ≥ 上游自身上限，如路径 4096、ids 500、id 正则同上游）；渲染层永远经 `window.*` 桥，禁止绕过。
2. **上游错误一律显式映射**：每个节点给出「上游抛出短码 → AppError 码」映射表并单测覆盖（K6 八码、K8 四码、K2 policyVersion 不匹配）；映射表集中且逐码注释，禁止 `catch {}` 静默吞——凡吞错处必须有等价 log（warn 级、含原始 message）或状态暴露（如 `classifySyncStartError` 先例）。
3. **兜底默认值**：能力开关默认全 false（`multiHostPairing`/`organizerEnabled`/在线解析同意 fail-closed）；列表/状态查询失败返回空集+错误字段，不抛穿 UI。
4. **破坏性能力**：仅 K8；确认语义见该节点；可逆性=Windows 回收站可恢复（本仓不做二次回收站）；执行前逐文件 sha256+size 复核由上游承担、helper 再复核一次（双保险）；`approval` 令牌一次性、中断不自动重放（上游构造期语义）。
5. **日志口径**：主进程 log 用英文（沿 `runtime-manager` 既有英文日志先例与 `src/**` 中文硬编码护栏）；用户可见文案一律 i18next，禁硬编码中文；**上游硬编码中文串（`state().message`/`lastResult`/`hint`）不透传渲染层**，按短码/状态枚举映射。

## 8. 测试设计总纲

1. **红灯先行**：每个行为子任务先写失败测试再实现；修复前已绿的测试必须重写为能抓住缺陷的形态（不允许「为绿而绿」）。
2. **三类覆盖**：正常 / 异常（上游抛错映射、未装配会话、开关关闭）/ 边界（上限值、空集、重复、截断、损坏文件）——每节点子任务表已逐条标注。
3. **链接态 vs 纯函数分工**：链接态（`*.linked.test.ts` + `describe.skipIf(!LINKED)` / `LINKED ? describe : describe.skip` 两种既有门控写法）覆盖真实上游模块行为（协议 diff、状态机、会话装配）；纯函数（未链接也必跑）覆盖本仓映射/解析/快照逻辑（`sync-server-view`、`protocol-contract`、`game-version` 映射、handler schema）。**新文件命名沿既有约定：链接态 `xxx.linked.test.ts`，纯函数 `xxx.test.ts`。**
4. **未链接默认态 skip 语义不得破坏**：所有新链接态测试必须用 `hasNikkiSyncLink(projectRoot)` 门控；未链接时 `npx vitest run src/main/nikkisync` 允许 skip 但不得 fail；已链接时 0 skip。
