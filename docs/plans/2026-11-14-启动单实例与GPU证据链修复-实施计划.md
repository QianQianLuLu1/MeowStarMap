## 一、三类现象的分别归因与关联关系

| 现象                           | 直接归因                                                                                                                                                                                                                                                                                                                                                                                                | 关联                                                                            |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| ① 双击无响应（无窗口、无报错） | a. GPU/Chromium 原生 FATAL 自杀（int3，无 JS 痕迹无弹窗，2026-08-19 问题机 54 个 dump 已裁决，见 `docs/packaged-scan-crash-report.md`）；b. 杀软/SmartScreen 静默拦截（进程根本未起）；c. `ELECTRON_RUN_AS_NODE=1` 全局环境变量导致打包 exe 以纯 Node 启动即退（e2e/launch-env.ts 已有先例记载）；d. 快捷方式指向旧版本/被移动的安装路径；e. 竞争实例的提示对话框被前台锁定策略遮挡，用户感知为"没反应" | a/d 由②③链路恶化：首次 GPU 闪退后若阶梯证据被污染，自愈降级不生效，反复表现为①② |
| ② 闪退无弹窗                   | a. | ③ 反复双击弹"已有实例运行"     | 对话框本身是**设计内保护**（`lifecycle.ts:85-221` 三选项）；异常在于：1) 重试窗口 3s < 退出清理 2-5s，正常重开也弹；2) 僵尸实例持锁（历史版本缺陷遗留，`lifecycle.ts:66-67` 注释）；3) 弹框后各修复项污染 GPU 证据与失败计数，事后软件"变卡变丑"                                                                                                                                                        | ①②的残留进程直接触发③；③的"清理并重启"路径又会制造新的假证据（见根因 5）        |

## 二、根因列表（按可能性/影响排序）

1. **【P0】GPU 兼容档误升级**：`exit-forensics.ts:173-187` `classifyPreviousExit` 对 `heartbeat.json` 无活性校验——文件存在且 last-exit bootId 不匹配即判 `native`。实例 A 运行中心跳每 5s 在写，此时启动的 B 在 `index.ts:108`（模块顶层、ready 前）读到"死亡证据"→ `gpu-fallback.ts:382` 档位 +1 并持久化 `fallbackActive`。
2. **【P0】连续失败计数被锁竞争实例污染**：`index.ts:226` `markBootAttempt()` 先于锁检查（`lifecycle.ts:72`，在 `bootstrapApplication` 内）执行；`FAILURE_THRESHOLD=2`（gpu-fallback.ts:54）→ 对运行中实例双击两次即触发下次启动强制兼容模式；锁失败实例永远到不了 `markBootSuccess()` 清零。
3. **【P0】心跳被第二实例覆写/删除**：锁失败实例仍执行 `initExitForensics()`（index.ts:189），覆写运行实例心跳、退出时 `will-quit` 删除，GPU 自愈证据链失真。
4. **【P1】锁重试窗口不足**：3×1s=3s < before-quit 清理耗时 2-5s（`lifecycle.ts:571-572` 自述）→ 正常"关闭后立即重开"弹"已有实例运行"。
5. **【P1】"清理并重启"制造假死亡证据**：taskkill /F 杀掉的进程留下陈旧心跳 → relaunch 后下一跳误判 native 白升档。
6. **【P2】原生模块预检在锁前**：`index.ts:197` 加载 better-sqlite3/koffi/sharp（数百 ms）后才轮到锁失败弹窗；坏环境下还可能以"启动失败"误导。
7. **环境性硬成因（不修代码，列入取证清单）**：GPU FATAL、杀软、`ELECTRON_RUN_AS_NODE`、快捷方式指向错误、VC++/ABI（打包已带 4 个 VC 运行库 DLL，`scripts/after-pack-vc-runtime.cjs`）。

## 五、修复方案（F1–F5）与 TDD 闭环

统一原则：每个节点先写失败测试（红灯）→ 改实现 → 重跑转绿（绿灯）→ 立即跑相关测试子集。红灯输出留存于本文档末尾《红绿记录》。

### 节点 1（F1）：心跳活性判定

- 文件：`src/main/app/exit-forensics.ts`、`src/main/app/__tests__/exit-forensics.test.ts`
- 改动：
  - `classifyPreviousExit(heartbeat, lastExit, isAlive?)` 增加可选第三参 `(pid: number) => boolean`；缺省时保持现行为（既有用例零改动）
  - 新增 `defaultIsProcessAlive(pid)`：`process.kill(pid, 0)`，`ESRCH`→false、`EPERM`→true、其余→false
  - `getPreviousExitEvidence(options?)` 与 `readStaleEvidence()` 接入：**心跳 pid 仍存活 → 无死亡证据（kind 'none'），不再记"外部终止"故障日志**
- 输入/输出：读 `userData/heartbeat.json`+`last-exit.json` → 返回 `PreviousExitEvidence`
- 验收：`npx vitest run src/main/app/__tests__/exit-forensics.test.ts` 全绿

### 节点 2（F2+F5）：赢家专属启动打点 + 原生模块预检后移

- 文件：`src/main/index.ts`、`src/main/app/lifecycle.ts`、`src/main/app/__tests__/lifecycle.test.ts`
- 改动：
  - index.ts whenReady 移除：`initExitForensics`+`markExitStage('when-ready')`（:186-193）、`verifyCriticalNativeModules` 块（:195-203）、`markBootAttempt`+`setupGpuProcessWatcher`（:224-228）
  - lifecycle.ts `lockAcquired = true`（:222）后依序插入：`verifyCriticalNativeModules`（失败→弹窗→releaseSingleInstanceLock→exit(1)，此时才真正持锁）→ `initExitForensics`+`markExitStage` → `markBootAttempt`+`setupGpuProcessWatcher`
  - index.ts 保留：`recordBootLevel`（ready 前硬约束，误判已被 F1 治愈）、`verifyStartupEnvironment`（廉价 fs 检查）、`registerRendererProtocol`、GPU 模拟崩溃分支
- 验收：`npx vitest run src/main/app/__tests__/lifecycle.test.ts` 全绿，现有 8 个单实例锁用例零回归

### 节点 3（F3）：清理重启前复位死亡证据

### 节点 4（F4）：锁重试窗口 3→6

- 验收：lifecycle.test.ts 全绿

### 节点 5（F6，e2e 验证中发现的补充根因）：NikkiSync 运行时初始化不得阻塞首窗

- **证据**（2026-11-15 e2e 复现两次 + 成功启动日志实测）：`initNikkiSyncRuntime` 内含游戏目录全盘发现，本机（未装游戏）实测 ~14s（main.log 00:53:04 → 00:53:18）；e2e 磁盘争用时超 30s 导致 firstWindow 超时。该 await 位于 `createMainWindow` **之前**——慢盘/多盘/无游戏的机器上这就是"双击后软件无响应"的直接机制之一，且与其自身注释"绝不阻塞启动"矛盾。
- 文件：`src/main/app/lifecycle.ts`、`src/main/app/__tests__/lifecycle.test.ts`
- 改动：`await initNikkiSyncRuntime(ctx)` 移到 `createMainWindow(ctx)` 之后（try/catch 与日志口径不变）；窗口先行，运行时后台就位，状态经 `IPC sync:getStatus` 对渲染层可见
- 红灯测试：`createMainWindow` 的 invocationCallOrder 必须 **早于** `initNikkiSyncRuntime`（修复前相反 → 必失败）
- 验收：lifecycle + nikkisync-runtime-setup + sync-server-setup 测试全绿

### 节点 6：打包版 e2e

- 文件：`e2e/second-instance.e2e.ts`（复用 `e2e/helpers.ts` `launchBuiltApp`、`--user-data-dir` 隔离、`e2e/launch-env.ts` 环境消毒）
