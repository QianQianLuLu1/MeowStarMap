## 一、根因结论

### 1.1 现象与两个数据源的差异

| 链路                      | 实现                                                                                                                                                                                                    | 结果                      |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------- |
| 左下角「图片 / 视频」数值 | `useGallerySummaryCounts`（`src/renderer/hooks/useGallerySummaryCounts.ts:32-48`）→ `hasMoreMedia === true` 时改用主进程 `GROUP BY file_type` 真值（`src/main/database/media-repository.ts:1235-1267`） | 显示全库真值（如 1200）✅ |
| 图库板块列表              | `mediaFiles` 数组，首屏一页 `MEDIA_PAGE_SIZE = 500`（`src/renderer/stores/mediaStore.ts:314`）                                                                                                          | 停在 500 ❌               |

**推论**：左下角能显示 1200，逻辑上等价于 `hasMoreMedia === true` 且 `mediaTotalCount / typeCounts` 齐备。`hasMoreMedia` 只来自 `media-repository.ts:1132-1157` 的 `pageSize + 1` 探针（取到 501 行 ⇒ `hasMore=true`、`nextCursor≠null`）。
⇒ **数据库侧还有下一页，是渲染进程没有再发请求**。

已逐项排除的怀疑（均可证伪）：

- 分页参数硬编码：三处 500（`mediaStore.ts:314`、`media-handler.ts:184`、`media-repository.ts:1071`）都是**单页大小**，不是列表上限，且被 `scripts/__tests__/media-page-limit-guard.test.ts` 钉为同源。
- 接口返回数量限制：`listMedia` 用 `LIMIT pageSz + 1` 探针，语义正确。
- 前端渲染截断：`src/main` 与 `src/renderer` 全量检索无 `slice(0, 500)`、无 `MAX_ITEMS`；`useFilteredMediaFiles` 只 filter/sort 不裁剪。
- 内存溢出保护：唯一的页数硬顶 `MAX_DEPTH_PAGES = 200`（10 万条），与 500 无关。

### 1.2 断点：逐页拉齐只有「一次性触发、无重试」

`src/renderer/hooks/useFilteredMediaFiles.ts:99-104`

```ts
useEffect(() => {
  if (hasMoreMedia && currentView !== 'recycle-bin') {
    void loadNextMediaPage() // 只尝试一次，返回值被丢弃
  }
}, [hasMoreMedia, mediaCount, currentView])
```

`loadNextMediaPage`（`src/renderer/stores/mediaStore.ts:825-862`）有四条**静默返回、不改任何 state** 的出口：

| 出口                    | 位置   | 触发场景                                          |
| ----------------------- | ------ | ------------------------------------------------- |
| `loadingMore` 为真      | `:832` | 触底续页在途                                      |
| `depthFetchActive` 为真 | `:832` | 整刷在途（扫描 / 批量缩略图期高频）               |
| 取数失败                | `:845` | `loadMoreMedia` 内部 catch 返回 null              |
| 被整刷顶掉              | `:849` | `cursorWriteAtEntry !== mediaCursorWriteSeq` 弃权 |

任一出口命中后：`hasMoreMedia` 仍为 `true`、`mediaFiles.length` 仍为 500、`currentView` 未变 ⇒ effect 三个依赖全未变化 ⇒ **effect 永不重跑 ⇒ 永久停在第 500 张**。

而整刷入口的深度取自「当前已加载条数」（`GalleryPage.tsx:228`、`mediaStore.ts:754`），停在 500 时它也只取 500 ⇒ 自我强化，列表永远长不回来。

### 1.3 放大器：无 limit 的整刷把列表缩回 500

`GalleryPage.tsx:205-218`（首屏 / 切视图）与 `:245-260`（读回数据源）调用 `fetchMediaFromDatabase()` **不传 limit** ⇒ `targetDepth = MEDIA_PAGE_SIZE`（`mediaStore.ts:630`）⇒ 已滚到 1200 的列表被整份替换成 500，游标一并复位。keep-alive 下图库 / 收藏 / 截图是三个 `GalleryPage` 实例共享同一 store（`App.tsx:320/333/336`），任一实例的 `currentView` 变化都会触发缩回。

### 1.4 既有测试把 bug 钉成了契约

`src/renderer/hooks/useFilteredMediaFiles.count.test.ts:148-187` 断言「续页失败后停在 500、`listMock` 只被调用一次」，当前为绿 —— 断言的正是本次要修的故障形态。按「测试必须覆盖 bug 场景」原则删除，并以「瞬时失败可恢复 / 持续失败有界重试 / 闸门解除可恢复」三条新用例替代（保留其「不得无限重试」原意）。

## 四、修复设计

### T1 `src/renderer/stores/mediaStore.ts` — 新增「拉齐泵」+ 刷新重启信号

**输入 / 输出**：`fillRemainingMediaPages(): Promise<void>`，无入参、无返回值、**永不抛异常**。

```ts
const FILL_RETRY_DELAYS_MS = [150, 300, 600, 1200]   // 4 次退避重试，合计约 2.25s
let fillPumpActive = false   // 单飞：4 个 useFilteredMediaFiles 消费方合并成一条链

export async function fillRemainingMediaPages(): Promise<void> {
  if (fillPumpActive) return
  fillPumpActive = true
  try {
    let idleAttempts = 0
    let pages = 0
    while (useMediaStore.getState().hasMoreMedia && pages < MAX_DEPTH_PAGES) {
      const before = useMediaStore.getState().mediaFiles.length
      await loadNextMediaPage()                 // 复用既有并发保护 / 去重 / 游标推进
      pages += 1
      if (useMediaStore.getState().mediaFiles.length > before) { idleAttempts = 0; continue }
      if (!useMediaStore.getState().hasMoreMedia) break
      if (idleAttempts >= FILL_RETRY_DELAYS_MS.length) { console.warn(...); break }
      await new Promise<void>((r) => setTimeout(r, FILL_RETRY_DELAYS_MS[idleAttempts++]))
    }
  } finally {
    fillPumpActive = false
  }
}
```

同时：

- `MediaState` 增加 `mediaRefreshEpoch: number`（初值 `0`）。
- `fetchMediaFromDatabase` 的 `finally`（`:738-742`）在释放 `depthFetchActive` 的同时 `mediaRefreshEpoch += 1` —— 语义为「一轮整刷结束、闸门已放开」，供拉齐链重启。

**不改** `loadNextMediaPage` / `listMedia` / IPC handler：单页上限 500 是刻意设计。

### T2 `src/renderer/hooks/useFilteredMediaFiles.ts` — 一次性触发改为拉齐泵

```ts
const mediaRefreshEpoch = useMediaStore((s) => s.mediaRefreshEpoch)
...
useEffect(() => {
  if (hasMoreMedia && currentView !== 'recycle-bin') {
    void fillRemainingMediaPages()
  }
}, [hasMoreMedia, mediaCount, currentView, mediaRefreshEpoch])
```

- **原样保留** `if (hasMoreMedia && currentView !== 'recycle-bin')` 文本：守卫测试 `scripts/__tests__/media-page-limit-guard.test.ts:108-115` 用正则钉住，且文件内不得出现 `viewMode`。
- import 增补 `fillRemainingMediaPages`；若 `loadNextMediaPage` 不再被引用需一并移除（`noUnusedLocals`）。

### T3 `src/renderer/pages/GalleryPage.tsx` — 两处整刷对齐「已加载深度」

- `:209` 与 `:253`：`fetchMediaFromDatabase()` → `fetchMediaFromDatabase({ limit: Math.max(MEDIA_PAGE_SIZE, useMediaStore.getState().mediaFiles.length) })`。

- `MEDIA_PAGE_SIZE` 已在文件内 import（`:228` 在用）。

## 五、错误处理

| 异常分支                             | 处理                                                     | 兜底                                                     |
| ------------------------------------ | -------------------------------------------------------- | -------------------------------------------------------- |
| `window.electronAPI.media.list` 缺失 | 返回 null → 泵判无进展 → 退避重试 → 阶梯耗尽告警退出     | 保留已加载 500，`hasMoreMedia` 保持 true，计数仍显示真值 |
| IPC 抛错（`IpcError`）               | `loadMoreMedia` catch 并 `console.error`，返回 null      | 不向 UI 抛错、不弹 toast                                 |
| 响应畸形（无 `files`）               | 返回 null                                                | 同上                                                     |
| `nextCursor` 不推进 / 谎报 hasMore   | 去重后无新增 ⇒ 长度不变 ⇒ 计一次无进展                   | 阶梯耗尽退出，不死循环                                   |
| 整刷顶掉                             | 闸门释放或 epoch 变化后重启                              | 已加载数据不丢                                           |
| 泵自身抛错                           | `try/finally` 复位单飞闸，函数不向外抛                   | 不因一次异常永久卡住                                     |
| 组件卸载                             | 泵为全局数据任务，不随卸载取消；阶梯有限（合计约 2.25s） | 无长期定时器泄漏                                         |

日志规则（仅 `warn` / `error`，英文串 + 结构化字段）：

- `[mediaStore] auto-fill stalled { loaded, idleAttempts, pages }`
- `[mediaStore] auto-fill hit page cap { pages }`

## 六、参数校验

| 对象                                | 类型              | 必填 / 默认                | 边界与非法值                                                        |
| ----------------------------------- | ----------------- | -------------------------- | ------------------------------------------------------------------- |
| `fillRemainingMediaPages()`         | 无入参            | —                          | 重复调用由 `fillPumpActive` 吞掉（幂等）                            |
| `hasMoreMedia`                      | `boolean`         | 初值 false                 | 非 true 不启动泵                                                    |
| `mediaFiles.length`                 | 非负整数          | —                          | 唯一的「是否有进展」判据                                            |
| `pages`                             | 计数              | 0 起                       | 达 `MAX_DEPTH_PAGES`(200) 即 break 并告警                           |
| `idleAttempts`                      | 计数              | 0 起                       | 达阶梯长度(5) 即 break，有进展归零                                  |
| `mediaRefreshEpoch`                 | `number` 单调递增 | 初值 0                     | 仅作 effect 依赖比较                                                |
| `fetchMediaFromDatabase({ limit })` | `number` 目标深度 | 不传仍为 `MEDIA_PAGE_SIZE` | 单页 `Math.min(targetDepth, 500)` 恒不越界；IPC zod `max(500)` 不变 |
