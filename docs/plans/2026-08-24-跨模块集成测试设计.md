## 1. 背景与目标

项目已有约 180 个单元测试与 4 个名为 `*.integration.test.ts` 的场景测试，但调研确认
**不存在任何真正跨越模块边界的集成测试**：

- 没有 `wrapHandler + ipcMain.handle → 数据库 → 返回/广播` 的串联测试（所有触及 DB 的
  测试都用内存 SQL 桩；`scanner-handler.test.ts` 甚至把 `wrapHandler` 也 mock 掉了）。
- 没有 `preload call()` 解包与真实 handler 的串联测试（`preload.test.ts` 只 mock
  `ipcRenderer.invoke` 返回手工构造的响应）。
- 没有渲染层 store/hook → electronAPI → 主进程链路的测试（`mediaStore.integration.test.ts`
  止步于手写 `setMockApi` 桩）。
- 错误码契约（`AppError.toIpcError()` 输出 ↔ preload `IpcError` 还原 ↔ 渲染层
  `useErrorToast` 消费）任何两个相邻环节之间都没有串联测试。

**目标**：补齐主进程、渲染进程、preload/IPC、数据库、业务 store 与服务层之间的关键协作
链路测试，覆盖：扫描入库、媒体列表加载、重复检测、删除/回收站、启动诊断、错误处理、
IPC 返回值解包。

**硬约束**：

- 不改变任何 `src/` 生产代码行为；不修改现有测试。
- 基于现有 Vitest（1.6.1，pool: forks）与 Playwright `_electron` 体系。
- 明确 mock 边界、测试数据隔离、调用顺序与最终状态断言，避免只测试单个函数。

## 2. 关键环境约束（调研结论）

## 3. 总体架构

```
┌─────────────── Vitest 集成层（进程内组装） ───────────────┐
│  渲染层 store ─► 真实 preload call()/subscribe            │
│        ▲              │ ipcRenderer（transport 模拟）      │
│        │              ▼                                    │
│  media:updated   ipcMain handlers ◄── 真实 registerXxx +  │
│  广播回传            │  真实 wrapHandler / zod / pathGuard │
│                      ▼                                    │
│        真实 DatabaseManager + MediaRepository             │
│        （better-sqlite3 → node:sqlite 适配器，真实 SQL）   │
└───────────────────────────────────────────────────────────┘
┌─────────────── Playwright e2e 层（真实跨进程） ───────────┐
│  win-unpacked 产物 + 真实 Electron + 真实 better-sqlite3   │
│  临时 userData + 临时游戏目录夹具，验证同样的业务链路        │
└───────────────────────────────────────────────────────────┘
```

两层互补：Vitest 层提供快速、可注入故障、可精确断言内部状态的集成测试；e2e 层提供
真实进程边界（真 preload 脚本、真 IPC 序列化、真原生 SQLite）的最终验收。

## 4. 测试基建组件（`tests/integration/`）

### 4.1 `sqlite-adapter.ts` — node:sqlite 的 better-sqlite3 兼容适配器

把 `node:sqlite` 的 `DatabaseSync` / `StatementSync` 包装成生产代码消费的
better-sqlite3 API 面（经源码核对，消费面为 `prepare/exec/pragma/transaction/close`，
statement 消费 `run/get/all`）：

- `constructor(path, options?)` → `new DatabaseSync(path)`；暴露 `open` 属性。
- `prepare(sql)` 返回包装 statement：`run(...params)` 返回
  `{ changes, lastInsertRowid }`；`get/all` 行为对齐（无行时 `get` 返回 `undefined`）。
- `exec(sql)` 直通；`pragma(str)` 解析 `'journal_mode = WAL'` / `'quick_check'` /
  `'integrity_check'` 等形态并转为对应 SQL 执行与结果整形（返回数组形态与
  better-sqlite3 一致，供 `DatabaseManager` 分级校验逻辑消费）。
- `transaction(fn)` 用 `BEGIN/COMMIT/ROLLBACK` 包裹；嵌套时用 `SAVEPOINT` 支持
  （better-sqlite3 语义：嵌套事务失败只回滚到 savepoint）。
- 导出 `NodeSqliteDatabase` 与类型，供 `vi.mock('better-sqlite3', () => ({ default: ... }))`
  注入（`connection.ts` 用动态 `import('better-sqlite3')`，vitest 可正常拦截）。

### 4.2 `node-sqlite-guard.ts` — 运行时版本守卫

- `hasNodeSqlite(): boolean`：try `import('node:sqlite')` 探测，失败返回 `false`。
- 依赖真 DB 的套件一律 `describe.runIf(hasNodeSqlite())`；Node 20 环境自动 skip
  并在测试名中保留提示，便于 CI 日志排查。

### 4.3 `ipc-transport.ts` — 进程内 IPC 通道模拟

- **main 侧**：复用/扩展 `createElectronMock` 的 `ipcMain`（`handle/on/removeHandler`
  收集到 `handlers` Map）。
- **renderer 侧**：提供 `ipcRenderer` 对象，`invoke(channel, ...args)` 路由到 main 侧
  已注册 handler；**结果经 `structuredClone` 往返**，模拟 Electron IPC 序列化边界
  （函数/循环引用等不可序列化值会在此暴露）。
- **广播**：`ctx.getMainWindow()` 返回假窗口 `{ webContents: { send } }`，`send` 把
  `(channel, payload)` 投递给 renderer 侧 `ipcRenderer.on` 监听器。
- **故障注入**：允许替换 `invoke` 实现以模拟畸形响应（`IPC_MALFORMED_RESPONSE` 分支）。
- 该 transport 使**真实的** `src/main/preload/ipc.ts`（`call/subscribe/IpcError`）与
  `src/main/preload/api/*.ts` 各命名空间模块可在 node 环境直接运行。

### 4.4 `ctx-factory.ts` — HandlerContext 工厂

- 每用例 `fs.mkdtemp(path.join(os.tmpdir(), 'it-'))` 建临时 userData；`afterAll` 清理。
- `app.getPath` 桩指向临时目录；`DatabaseManager` 真实构造 + `initialize()` 真实执行
  （建目录、迁移、WAL pragma、quick_check）。
- 组装真实 `HandlerContext`：

| 成员                                                               | 真实/受控                                                       |
| ------------------------------------------------------------------ | --------------------------------------------------------------- |
| `dbManager`                                                        | 真实（适配器引擎）                                              |
| `scannerManager`                                                   | 真实 `ScannerManager`，utilityProcess 消息协议驱动              |
| `mediaWorkerManager`                                               | 受控桩（批次消息可手动推进）                                    |
| `taskScheduler`                                                    | 真实                                                            |
| `thumbnailGen`                                                     | 桩（集成链路不生成缩略图）                                      |
| `fileService`                                                      | 真实 `FileService` + 临时目录真实文件；`shell.trashItem` 三态桩 |
| `videoService` / `watermarkService` / `videoEditorBridge`          | 桩                                                              |
| `getMainWindow`                                                    | 假窗口（收集广播）                                              |
| `notifyMediaUpdated` / `invalidateMediaPathCache` / `applyUITheme` | 真实 `media-update` 逻辑或可断言的 spy                          |

- 按需调用**真实的** `registerXxxHandlers(ctx)`（来自 `src/main/ipc/handlers/`），
  **不 mock `validator.ts`**——这是与现有单测的关键区别。

### 4.5 Mock 边界总原则

- **真实执行**：`wrapHandler`/zod 校验、`pathGuard`、`MediaRepository` 全部 SQL、
  `DatabaseManager` 初始化与迁移、`preload call()/subscribe`、`FileService` 文件操作
  （限临时目录）、`AppError.toIpcError()` 序列化。
- **受控桩**：`shell.trashItem`、`utilityProcess`、`dialog.showMessageBox`、`koffi`、
  缩略图生成、媒体批次 worker。
- **绝不 mock**：`validator.ts`、数据库引擎（适配器即真实 SQLite）、preload 解包逻辑。

## 5. Vitest 集成测试矩阵（7 条链路 → 7 个文件）

所有文件命名 `*.integration.test.ts`（与现有命名惯例一致），依赖真 DB 的套件加
`describe.runIf(hasNodeSqlite())` 守卫。

### 5.1 错误处理 + IPC 解包往返 —

`src/main/ipc/__tests__/ipc-roundtrip.integration.test.ts`

- 链路：业务层抛 `AppError`（`notFound/forbidden/preconditionFailed/canceled/internal`）
  → 真实 `wrapHandler` 序列化 → transport → 真实 preload `call()` → `IpcError`。
- Mock 边界：仅业务函数为注入桩；包装、序列化、传输、解包全真实。
- 断言：
  1. `IpcError` 的 `code/message/userMessage/details` 与源 `AppError` 一一对应
     （错误码契约往返闭环，任何一侧字段改名都会在此失败）。
  2. zod 校验失败 → `VALIDATION_ERROR` + `details` 含 issues 结构。
  3. 畸形响应注入 → `IPC_MALFORMED_RESPONSE` 兜底。
  4. `subscribe` 收到主进程广播；退订函数调用后不再收到。

### 5.2 媒体列表加载 —

`src/main/ipc/__tests__/media-list.integration.test.ts`

- 链路：种子数据经真实 `MediaRepository` 写入临时 SQLite → `media:list` 全链
  （zod 校验 → `getRepo()` → `listMedia` → 响应整形）。
- 断言：
  1. 分页 `total/rows` 形状与 id 字符串化约定。
  2. `deletedOnly: true` 仅返回回收站行；默认查询排除回收站行。
  3. `hideDuplicates` / `accountUid` / `corruptedOnly` 过滤生效。
  4. 空库返回合法空结构（`{ total: 0, rows: [] }`）。

### 5.3 删除/回收站 —

`src/main/ipc/__tests__/delete-recyclebin.integration.test.ts`

- 链路：真实临时文件 + `file:delete`（trashItem 桩）→ `media:softDelete` → DB 状态
  → `media:restore` → `media:permanentDelete` / `media:emptyRecycleBin` 三阶段。
- 断言：
  1. 调用顺序：`softDelete → trashBatch → hardDeleteBatch`（sequence 断言）。
  2. 每步后的 DB 最终状态（软删标志、行数、物理文件存在性）。
  3. **故障注入**：`trashItem` 中途失败/文件缺失（三态）时行保留软删态、不做
     `hardDelete`；重试后成功则推进。
  4. 恢复后 `media:updated` 广播到达假窗口。

### 5.4 扫描入库 —

`src/main/scanner/__tests__/scan-ingest.integration.test.ts`

- 链路（两段）：
  - (a) 批量写：按 `worker-protocol` 构造 `SCAN_BATCH` 消息 →
    `src/main/database/worker/database-worker.ts` 入口
    （适配器经现有 `installBetterSqlite3Hook` 注入）→ 真实库行断言。
  - (b) 扫描编排：`scanner:start` → 真实 `pathGuard` 校验 →
    `ScannerManager/ScannerWorkerBridge` + mock utilityProcess 按协议发
    `SCAN_BATCH`/`SCAN_COMPLETE` → `runPostScanActions`。
- 夹具：临时目录树含 6-12 位数字 UID 段（如
  `.../GamePlayPhotos/123456789/a.jpg`），验证 `path-classifier` 的
  `uid/album_type/media_source` 分类落库正确。
- 断言：
  1. 入库行字段分类正确。
  2. 顺序：写库 → `import_roots` 记录 → `scanner:complete` 广播 → `notifyMediaUpdated`。
  3. 非法路径（敏感目录）被 `pathGuard` 拒绝，IPC 返回 forbidden 错误（经 transport
     还原为 `IpcError`）。

### 5.5 重复检测 —

`src/main/ipc/__tests__/duplicate.integration.test.ts`

- 链路：真实临时文件（两组同内容文件 + 一个异内容文件）种子入库 →
  `media:findDuplicates`（真实 fs sha256）→ `media:markDuplicates`
  （`mediaWorkerManager` 桩推进批次）→ `duplicate:listGroups`。
- 断言：
  1. 分组正确：同 size+hash 成组，异内容文件不入组，`pickBestId` 保留项符合规则。
  2. 标记后 DB 重复标志落库；`listGroups` 返回与库状态一致。
  3. `ProgressThrottle` 进度回调被触发（记录调用）。

### 5.6 启动诊断 —

`src/main/app/__tests__/startup-diagnosis.integration.test.ts`

- 链路 A（日志）：真实临时 userData 上 `diagLog` / `logStartupError` 落盘 →
  `readStartupErrors` 读回 → `clearStartupErrors` 清空。
- 链路 B（启动任务数据依赖，现有单测仅 stub 级断言）：真实 DB 种子
  `running` 状态 `scan_history` + 缺失文件的媒体行 →
  `cleanupInterruptedScanHistory` → `notifyInterruptedScan`（广播一次性消费）→
  `cleanupAndRepairDatabase`。
- 断言：
  1. 日志文件内容、轮转阈值行为。
  2. `running → interrupted`（R4 写入）→ 广播消费后转 `failed`（任务间数据依赖成立）。
  3. 文件缺失的媒体行被标记缺失；`scanner:interrupted` 广播到达。

### 5.7 渲染层全环 —

`src/renderer/stores/mediaStore.chain.integration.test.ts`（node 环境，与现有 `mediaStore.integration.test.ts` 同模式）

- 链路：真实 `preload/api/*` + transport 组装成 `window.electronAPI` →
  `mediaStore.fetchMediaFromDatabase` → transport → 真实 handler → 真 DB。
- Mock 边界：仅 `ipcRenderer` 由 transport 提供；preload、store、handler、DB 全真实。
- 断言：
  1. store 加载的列表数据与库内容一致（数量、字段）。
  2. 主进程侧触发 `media:updated` 后，`mediaStore` 订阅链路驱动刷新。
  3. handler 失败时 store error 态正确；`CANCELED` 类错误静默。

## 6. Playwright e2e 层 — `e2e/integration.e2e.ts`

真实 `win-unpacked` 产物 + 真 Electron + 真 better-sqlite3 + 真 preload。
复用 `e2e/helpers.ts` 的 `findUnpackedExe/launchApp/closeApp/collectDiagLogs`；
`launchApp` 以 `--user-data-dir` 指向每用例独立的 `mkdtemp` 目录实现数据隔离。

| 用例           | 内容                                                                                                                                                                                                | 数据隔离            |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| E1 扫描入库    | 构造临时游戏目录树（`GamePlayPhotos/<10位UID>/*.jpg`，≥3 张），`electronApp.evaluate` 内调 `window.electronAPI.scanner.start({ path })` → 等待 `scanner:complete` → `media.list` total 与文件数一致 | 每用例新 `mkdtemp`  |
| E2 列表加载    | `media.list` 响应形状 + `category.list` 一致性；关闭后二次启动数据仍在（持久化）                                                                                                                    | 复用 E1 的 userData |
| E3 删除/回收站 | `mediaAction.softDelete` → `deletedOnly` 列表可见 → `restore` → 回正常列表；物理文件全程不动                                                                                                        | 临时图片文件        |
| E4 重复检测    | 两份相同内容文件入库 → `findDuplicates` 返回 1 组                                                                                                                                                   | 临时文件            |

- 串行单 worker（沿用现有 `playwright.config.ts` 配置），用例超时 60s；
  失败时 `afterAll` 钩子收集诊断日志（复用现有机制）。
- 普通标签，随 `e2e:smoke`（`--grep-invert @perf`）在 CI build job 的
  `dist:win` 之后自动执行。

## 9. 非目标（明确不做）

- 不验证 WAL 多进程并发写一致性（需真实多进程环境，属性能/冒烟范畴）。
- 不重编译或替换 better-sqlite3 二进制。
- 不修改迁移脚本本身；仅在真实引擎上执行并观察结果。
- 不覆盖解密（koffi dll）、视频编辑 worker、插件系统等与本次 7 条链路无关的域。
- 不改现有 10 分片 test job 的 Node 版本。

## 10. 风险与缓解

| 风险                                                                           | 缓解                                                                             |
| ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
